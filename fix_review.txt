2. 按 fix-bug.md 流程修复代码
3. 修复后运行 black . --line-length 100 && isort .
4. 运行 pytest tests/ -q -m "not slow"
5. 如果测试失败，读取报错信息继续修复

# 修复 Bug 提示词

## 角色
你是一名面向本仓库的调试与修复专家。

## 常见问题类型
- 基线编码与检索不一致
- 评测指标计算错误
- 数据集加载或缓存问题
- 日志、随机种子、设备工具回归
- 因 API 或命名漂移导致的测试失败

## 排查流程
1. 用最小输入复现问题
2. 定位失败层：`utils` / `baseline` / `vector_store` / `evaluation` / `tests`
3. 检查日志、堆栈和失败测试
4. 对照 `docs/` 与当前代码规范
5. 修复根因，而不是只修表象

## 修复要求
- 为 bug 场景新增或更新单元测试
- 新增或修改代码保持类型注解完整
- 优先采用最小、定向的修改
- 先运行相关测试子集，再视情况运行完整测试

## 验证

## 问题列表

### [高] 模块边界 / 依赖方向
**文件**: `src/baseline/benchmark.py:38`
**问题**: `build_benchmark_context` 新增了对 `ELFPipeline` 的直接导入和实例化（L141-143），形成 `baseline → elf` 的反向依赖。`baseline` 模块原本是"基础层"（文档编码、建索引入口），现在内部耦合了 ELF 专用逻辑。后续如新增第三种 method，`build_benchmark_context` 会继续膨胀。
**建议**: 将文档编码器的"按 method 选择"逻辑抽到 `src/evaluation/orchestrator.py`，或引入一个轻量工厂函数 `src/utils/encoder_factory.py`（接收 `method` 返回 `(encoder, elf_pipeline)`）。`build_benchmark_context` 保持接收已构造好的 encoder/elf_pipeline，不要自己 new。

### [高] 测试断言虚设——未验证 ELFPipeline 是否被构造
**文件**: `tests/test_benchmark.py:186-193`
**问题**: `test_build_context_baseline_docs_use_bge` 断言 `self._elf_pipeline_mock.enhance.call_count == 0`。但 `self._elf_pipeline_mock` 是在 `setup_method` 中创建的独立 MagicMock，**从未被注入**到被测系统（`build_benchmark_context` 在 `method='baseline'` 时不调用 `ELFPipeline()`，所以这个 mock 全程闲置）。断言 trivially 通过，但没有真正验证 "ELFPipeline 未被构造"。
**建议**: 在该测试中额外 patch `src.baseline.benchmark.ELFPipeline`，然后 assert 该 patch 的 `call_count == 0`。

### [中] 重复采样逻辑——两处拷贝
**文件**: `experiments/diagnose_elf.py:191-202` vs `src/baseline/benchmark.py:118-129`
**问题**: `_rebuild_context_from_vectors` 中的采样逻辑（qids_with_qrels → referenced → DatasetTriple）与 `build_benchmark_context` 完全一致，逐字拷贝。后续若调整采样策略，两处必须同步修改，容易遗漏。
**建议**: 将采样逻辑提取为公共工具函数（例如 `src/utils/sample.py` 中 `sample_dataset(data, n)`），两处调用同一函数。

### [中] `encoder_name` 参数对 `method='elf'` 是 dead argument
**文件**: `src/baseline/benchmark.py:79`
**问题**: `build_benchmark_context(encoder_name=...)` 在 `method='elf'` 分支中完全不使用（仅 `method='baseline'` 时传给 `BaselineEncoder`）。但签名中它是必选参数（有默认值 `DEFAULT_ENCODER`），导致 `method='elf'` 的调用方仍须传入一个无意义的 `encoder_name` 值。
**建议**: 将 `encoder_name` 的默认值设为 `None`，在 `method='baseline'` 分支中 fallback 到 `DEFAULT_ENCODER`；或将其改为 keyword-only 并在非 baseline 时不校验。

### [中] `_encode_queries_elf_raw` 存在隐式入参修改
**文件**: `experiments/diagnose_elf.py:260-261`
**问题**: `if ctx.elf_pipeline is None: ctx.elf_pipeline = ELFPipeline()` — 函数直接修改入参 `ctx` 的属性。虽然 `_encode_queries_elf` 有同样模式（一致），但这属于副作用，调用方不易察觉。
**建议**: 在 `_prepare_docs` 阶段就确保 `ctx.elf_pipeline` 已初始化（`_rebuild_context_from_vectors` 的 ELF 分支已经做了），然后在 `_encode_queries_elf_raw` 中改为 `assert ctx.elf_pipeline is not None`，或通过 `ctx.elf_pipeline` 做 defensive get。

### [中] 缺少针对 elf-raw / `_analyze_group` 新参数的直接测试
**文件**: `tests/test_benchmark.py` / `tests/test_orchestrator.py`
**问题**: `_analyze_group` 重构后新增 `baseline_top10` 参数（分离 overlap 与 shift 的计算），`_encode_queries_elf_raw` 是诊断关键新增函数——两者均无直接单元测试。当前测试仅覆盖 `build_benchmark_context` 和 `run_grid` 的集成行为。
**建议**: 为 `_analyze_group` 增加参数组合测试（仅 qvecs / 含 base_qvecs / 含 baseline_top10 / 全部），为 `_encode_queries_elf_raw` 增加 smoke test。

### [低] `n_docs` JSON 输出类型变化（向后不兼容）
**文件**: `experiments/diagnose_elf.py:518`
**问题**: `n_docs` 从 `int` 变为 `{"baseline": N, "elf": M}`。若有下游脚本解析 `diagnosis.json` 的 `n_docs` 字段，会因类型变化而 break。
**建议**: 风险低（诊断脚本输出多为一次性消费），但可在 changelog 或 commit message 中注明。

### [低] 不必要的 `print()` 调用
**文件**: `experiments/diagnose_elf.py:530`
**问题**: `print(report_md)` 在 `_main()` 中用于 CLI 输出。虽然同类代码 `src/baseline/benchmark.py:364` 也有 `print(df.to_markdown())`（两者都在 `if __name__ == "__main__"` 路径上），但按审查标准的严格解释，库文件中的 `print()` 应改为 `logging`。由于这两处是 CLI 入口的主观输出（不是调试打印），风险极低。
**建议**: 保持现状可接受；若要严格合规，可改用 `logger.info()` 并将 report 作为单条日志输出，或通过 `sys.stdout.write()` 明确表达"这是 CLI stdout"语义。

### [低] `html/elf-root-cause-analysis.html` 放置位置
**文件**: `html/elf-root-cause-analysis.html`（新增）
**问题**: 项目已有 `docs/` 目录存放计划和设计文档。该 HTML 是一份根因分析报告，放在顶层 `html/` 新目录中，与既有结构不一致。
**建议**: 移到 `docs/analysis/` 或 `experiments/outputs/nfcorpus/diagnosis/` 下，与 `diagnosis.md` 放在一起。

### [低] `test_build_context_baseline_docs_use_bge` 接收无用的 `tmp_path` fixture
**文件**: `tests/test_benchmark.py:186`
**问题**: 函数签名包含 `tmp_path` 但未使用，mypy/pylint 会报警。
**建议**: 移除 `tmp_path` 参数，或通过 `@pytest.mark.usefixtures("tmp_path")` 隐式注入。

+<section>
+  <h2>3. 根因分析(三层)</h2>
+
+  <h3>3.1 直接原因: 查询向量与文档向量不在同一向量空间</h3>
+  <p>评测的双链路设计(计划 §2.2/§2.3, <code>docs/diffusion-rag-plan.md</code>)是
+  <strong>"同一向量库, 仅替换查询编码"</strong>:</p>
+  <ul>
+    <li><strong>文档侧</strong>(两条链路共享): BGE 编码器 <code>BAAI/bge-base-en-v1.5</code> → 768-dim;</li>
+    <li><strong>baseline 查询侧</strong>: 同一个 BGE 编码器 → 768-dim, 与文档同空间, 内积正常(0.466);</li>
+    <li><strong>ELF 查询侧</strong>: <code>ELFNativeEncoder</code>(T5-small + 投影层) → 768-dim, 但这是
+      <em>另一个独立训练的向量空间</em>。</li>
+  </ul>
+  <p>两个空间虽然<strong>维度相同(768)</strong>, 但 BGE 与 T5 投影是各自独立训练的, 没有对齐约束。
+  单位向量在不同空间中点积期望接近 0——这正是 0.007 的来源。计划文档中
+  "向量维度: 768(与 ELF 输出对齐)"(plan §2.2)隐含了<strong>"同维即对齐"</strong>的假设, 该假设被数据否定。</p>
+
+  <h3>3.2 深层原因一: 扩散增强使用"占位速度场", 无真实 denoiser</h3>
+  <p>即使空间错位的问题不存在, 当前增强链路也<strong>没有接入真实训练过的去噪模型</strong>。
+  <code>ELFPipeline</code> 的默认速度场是 <code>_default_model_fn</code>(向原点收缩的简易近似,
+  代码注释明确写着"当真实扩散模型不可用时回退使用"), 且噪声调度 <code>σ(t)=t</code> 在
+  <code>noise_t=0.3~0.6</code> 下会注入相当强度的噪声。去噪输出与原始向量相关性极低
+  (<code>shift_cos=0.026</code>), 增强并未产生"语义增强", 而是把向量推离了原始方向。</p>
+
+  <h3>3.3 深层原因二: 扩散噪声尺度与向量分布不匹配</h3>
+  <p>即使速度场正确, <code>add_noise</code> 用 <code>z_t = z_0 + σ(t)·ε</code> 加噪, 其中
+  <code>σ(t)=t</code>。对单位向量, <code>noise_t=0.5</code> 意味着噪声能量为信号能量的 50%,
+  向量已严重污染; 若去噪不精确(见 3.2), 输出将远离 <code>z_0</code>。这也是
+  <code>shift_l2≈1.40</code>(接近两个随机单位向量的期望距离)的原因。</p>
+</section>

+  (仅 5 篇文档全部被返回)的假象; sample=20(542 篇文档)下该列为 0.0, 具备有效区分度。
+  诊断脚本已固化 elf-raw 对照(<code>experiments/diagnose_elf.py</code>), 后续可直接复现。</p>

+<!-- ============ 6. 解决办法 ============ -->
+<section>
+  <h2>6. 可能的解决办法(按成本从低到高)</h2>
+
+  <h3>方案 A: 先验证, 再对症下药(必做, 零成本)</h3>
+  <p class="step">执行第 5 节实验, 确认错位层。后续方案按实验结果选择。</p>
+
+  <h3>方案 B: 文档侧也使用 ELF 编码器(若错位在编码层, 首选)</h3>
+  <p class="step">把文档向量库也换成 <code>ELFNativeEncoder</code> 编码, 使查询与文档落在同一
+  (ELF) 空间, 双链路各自"自洽":</p>
+  <ul>
+    <li><strong>改动点</strong>: <code>run_benchmark</code> 文档准备阶段按 method 切换编码器(当前恒用 BGE);
+      或为 ELF 链路单独建索引(放弃"双链路共享索引"计划假设);</li>
+    <li><strong>代价</strong>: 全库文档重新编码(CPU 上 nfcorpus 542 篇约 8 分钟, 有缓存机制可复用);
+      文档量大的数据集耗时显著, 可配合批量编码 <code>encode_batch</code>;</li>
+    <li><strong>效果</strong>: 保证 ELF 链路检索有效(相似度从 0.007 回到正常水平), 指标才能反映
+      "增强"的真实效果。</li>
+  </ul>
+
+  <h3>方案 C: 接入真实扩散 denoiser, 校准噪声调度(若错位在扩散层)</h3>
+  <ul>
+    <li>用训练过的 velocity/score 模型替换 <code>_default_model_fn</code> 占位实现
+      (<code>ELFPipeline(model_fn_cond=..., model_fn_uncond=...)</code> 已预留注入接口);</li>
+    <li>校准 <code>sigma(t)</code> 与 ELF 训练时一致, 或降低 <code>noise_t</code>(如 0.1~0.2)
+      使去噪更易收敛; 增加 <code>steps</code> 验证 ODE 收敛性;</li>
+    <li>检查 <code>denoise_with_cfg</code> 数值稳定性(dt 符号、t_start 推断)。</li>
+  </ul>
+
+  <h3>方案 D: 使 ELF 输出空间与 BGE 对齐(若必须保持共享索引)</h3>
+  <ul>
+    <li>用 BGE 文档/查询向量作为监督目标, 微调 <code>_projection</code>(或加一层可学习对齐变换);
+      ELF 增强在"已对齐"的 BGE 空间内进行;</li>
+    <li>代价最高(需要训练数据/目标函数), 仅在双链路必须共享同一向量库且不能换文档编码时考虑。</li>
+  </ul>
+
+  <h3>方案 E: 短期降噪实验(快速试错)</h3>
+  <p class="step">若想快速确认扩散链路影响, 可临时把 <code>noise_t</code> 降到 0(等于不做扩散,
+  只走 ELF 编码), 对比指标:
+  <code>query_doc_sim</code> 若仍 ≈ 0.007 → 编码错位坐实, 直接转方案 B。</p>
+</section>
