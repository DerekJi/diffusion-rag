## 问题列表

### [高] 错误处理 / ELF 模型加载无异常保护
**文件**: `src/baseline/benchmark.py:135`
**问题**: `ELFPipeline()` 初始化位于 `run_benchmark()` 内部，没有任何 `try/except` 包裹。ELF 模型首次运行需联网下载权重，网络失败、磁盘不足或模型不兼容会导致未捕获异常直接崩溃。对比同类代码 `BaselineEncoder.__init__` (encoder.py:41-45) 有明确的 `try/except RuntimeError` 保护。
**建议**: 在 `ELFPipeline()` 调用处增加异常处理，至少捕获后给出可操作的错误信息：

```python
try:
    elf_pipeline = ELFPipeline()
except Exception as e:
    logger.error("ELF 模型加载失败 (可能需要联网下载权重): %s", e)
    raise RuntimeError(f"ELF 模型加载失败: {e}") from e
```

---

### [中] 重复代码 / argparse 定义在两处重复维护
**文件**: `src/baseline/benchmark.py:194-223` 与 `src/evaluation/runner.py:44-73`
**问题**: 两个模块各自定义了几乎相同的 `argparse` 参数解析器（`_main()` 和 `main()`），参数名、默认值、help 文本完全重复。未来新增参数需要同步修改两处，容易遗漏导致行为不一致。`runner.py` 本质上是 `run_benchmark()` 的薄封装，直接复用 `benchmark.py:_main()` 的 parser 构建逻辑即可消除重复。
**建议**: 将 `benchmark.py` 的 argparse 构建提取为模块级 `_build_parser()`，`runner.py` 直接 import 复用；或让 `runner.py` 直接调用 `benchmark.py:_main()` 而非重写 CLI。

---

### [中] 函数签名 / `run_benchmark` 参数过多（12 个）
**文件**: `src/baseline/benchmark.py:46-58`
**问题**: `run_benchmark()` 当前有 12 个参数，且随 Phase 推进可能继续增长（如 Phase 4 Colab 模式参数、Phase 5 repeats 参数等）。参数过多降低可读性和调用便利性——每次调用需按位置或显式关键字排列大量默认值。
**建议**: 考虑引入 dataclass 或 `TypedDict` 收敛配置：

```python
from dataclasses import dataclass

@dataclass
class BenchmarkConfig:
    dataset: str = "nfcorpus"
    method: str = METHOD_BASELINE
    encoder_name: str = DEFAULT_ENCODER
    # ...
    elf_steps: int = DEFAULT_ELF_STEPS
    elf_noise_t: float = DEFAULT_ELF_NOISE_T
    elf_cfg_scale: float = DEFAULT_ELF_CFG_SCALE

def run_benchmark(config: BenchmarkConfig) -> pd.DataFrame: ...
```

这并非阻塞性问题，但建议在 Phase 4 前重构。

---

### [中] 命名 / `build_parser()` 应为私有函数
**文件**: `src/evaluation/runner.py:38`
**问题**: `build_parser()` 仅在 `main()` 中调用，且不是模块 `__all__` 导出的公共 API。按仓库命名规范（`.reasonix/python-naming-conventions.instructions.md` §3），私有辅助函数应使用 `_` 前缀。测试直接导入它验证参数解析，但测试可以导入私有函数（Python 无访问控制）。
**建议**: 重命名为 `_build_parser()`，同步更新 `test_runner.py:10` 的 import。

---

### [低] 风格 / `raise SystemExit(main())` 不够地道
**文件**: `src/evaluation/runner.py:115`
**问题**: `raise SystemExit(main())` 虽然功能等价于 `sys.exit(main())`，但这是利用异常机制做控制流，且 `SystemExit` 作为异常类的语义是"被引发的异常"而非"主动退出"。标准 Python CLI 写法是 `sys.exit(main())`（如 CPython 官方指南和 `argparse` 文档推荐）。
**建议**: 改为 `import sys` + `sys.exit(main())`。

---

### [低] 代码规范 / CLI 入口使用 `print()` 输出
**文件**: `src/baseline/benchmark.py:241` 与 `src/evaluation/runner.py:110`
**问题**: 两处 CLI 入口都用 `print(df.to_markdown())` 输出结果表格，并有注释标注 "intentional"。审查标准要求库代码使用 `logging` 而非 `print()`。此处属于 CLI 入口点（`__main__` 或 `main()`），直接输出到 stdout 是其职责，使用 `print()` 合理。**但** `benchmark.py` 同时也是库模块（`run_benchmark` 被 `runner.py` 导入），`_main()` 内部的 `print()` 不影响库调用路径。
**建议**: 当前可接受，但建议后续统一使用 `logger.info()` 记录结果路径，`print()` 仅保留最终表格输出并在注释中说明理由。无需立即修改。

---

### [低] 类型 / `SUPPORTED_METHODS` 更适合用 `frozenset`
**文件**: `src/config.py:23`
**问题**: `SUPPORTED_METHODS: tuple[str, ...]` 语义上是"合法值集合"，用 `frozenset` 更直观（不可变、无序、无重复）。当前 `tuple` 也可正常工作（`argparse.choices` 接受 tuple），但若未来需要做 `method in SUPPORTED_METHODS` 的 O(1) 查找，`frozenset` 更合适。
**建议**: `SUPPORTED_METHODS: frozenset[str] = frozenset({METHOD_BASELINE, METHOD_ELF})`。非阻塞。

---
